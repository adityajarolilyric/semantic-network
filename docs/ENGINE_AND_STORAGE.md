# Shared SQL engine and physical storage

Managed identity/pivot, planning populations, resolved transactions, measures, Decision View and edits share one engine. Domain services submit typed intent and expected versions; planners resolve meaning; compilers generate SQL; executors run checks/write candidates; MongoDB manifests activate results. Do not add a separate SQL-string service per feature.

## Backend module boundaries

The engine is organised by responsibility; package initialisers contain no eager imports. Resource APIs/services, MongoDB repositories and warehouse adapters retain their existing roles. No new framework, dependency, metadata format, policy version or migration is introduced by this refactor.

- **`engine/graph/`:** detached effective schemas, grain contexts, relationships, placement/compatibility and dependency analysis. Pure functions consume captured metadata. `execution/inputs/schema.py` owns repository-backed schema loading and calls the pure graph expansion.
- **`engine/sql/`:** logical/execution contracts, CTE context/checkpoints, shared-read ASTs, diagnostic formatting and pure storage/read SQL helpers. Compilation never reads repositories or executes SQL. Quoting remains in `warehouse/sql.py`.
- **`engine/transformations/`:** the input pipeline, Filters, Pivot, Date/Calendar resolution and Multi-grain resolution. Pivot/Date stages keep separate planning and compilation. Multi-grain compilation coordinates input preparation, profile matching and last-assignment overlay; profile discovery that executes queries lives in `execution/inputs/resolution_profiles.py`.
- **`engine/populations/`:** population planning/compilation, transformed inputs, virtual populations and Transaction-owned population queries. The existing `DimensionPlan` and Dimension metadata vocabulary remain compatible.
- **`engine/measures/`:** a small `MeasureCompiler` facade owns operation-local state and delegates to native, formula, alignment, propagation, value-conversion and output compilers. Aggregation, counting, range aggregation and dependencies have focused modules. `contracts.py` owns value-state markers, compiler policy versions and derivation records.
- **`engine/decision/`:** field resolution, view relationships, source planning, read compilation and edit planning. Editable allocation and patch compilation are separate collaborators. The existing specialised compiler overrides remain to preserve incremental/read/edit dispatch; no new inheritance hierarchy or mixins are introduced.
- **`engine/execution/`:** jobs, worker fencing, read admission/leases, input capture, builds, artifact recovery, sorting and SQL history. `builds/measures.py` coordinates preparation → per-population materialisation → activation. These phases share one explicit `PreparedMeasureBuild`, preserving compiler caches, completed dependency checkpoints, ordering, error cleanup and activation fences.

Services submit intent and use repositories; they do not generate SQL or create database clients. Warehouse adapters execute compiled plans, mutations and table publication. `WarehouseCheckRunner`, `ArtifactCollector` and `TableStorage` are imported directly from their owning warehouse modules; obsolete engine forwarding files are removed. Metadata activation remains in `repositories/metadata/activation.py`.

Application-scoped services and stateless execution collaborators are reused. Compiler contexts, memoised captures, CTEs, checks, caches and compiler collaborators belong to **one operation** and must never be singletons. Collaborators receive the owning compiler to share its context and preserve specialised dispatch; they do not copy the graph or construct another compiler. New transformation/build state travels through small explicit contracts rather than growing loosely related fields on coordinators.

### Refactor verification and extension rules

`test_engine_architecture.py` checks that planning packages have no repository/service dependencies or async execution, runtime engine imports remain acyclic, and compiler collaborators have isolated operation state. `test_engine_sql_regression.py` compares fingerprints of SQL, validation checks, output schemas, compiler versions and unavailable-measure outcomes against the pre-refactor canonical Product/Location/Time example. The golden contract includes five populations and both native/Base and coarser measure outputs. Fingerprints must not be regenerated merely to make a structural refactor pass.

Keep these boundaries when extending the engine: planners establish semantics, compilers render plans, execution captures/runs/publishes, and persistence adapters own database access. Do not add general-purpose `utils.py` modules, eager package re-exports or global compiler/result caches. A feature that changes mathematics or storage policy needs its own reviewed change, separate from file organisation.

## Shared engine operators and compatibility

The November 2026 simplification keeps Base selection, representation placement, HTTP/Mongo contracts and stored evaluation fingerprints unchanged. No migration or Full Refresh is required.

- **Resolved metadata:** `ResolvedGraph` owns detached grain contexts and indexes by ID/kind for one operation. Effective schemas additionally use `EffectiveGraph`; validation, relationship analysis, manifests and compilers reuse it. The sequence/indexes are read-only; nested documents are read-only by convention. Authoring changes create replacement documents and resolve again. Explicit managed-schema changes always reapply the resolver. There is no process-wide metadata/result cache.
- **Aggregation:** `AggregationPlan` records removed Time/NonTime axes, intermediate grouping and configured order. `AggregationOperator` renders the stages with SQLGlot, preserving NULL, incomplete coverage, Mixed and first/last ordering. Materialisation rollups and Decision View use this operator. Native fact aggregation, range allocation and edit distribution remain their distinct domain operations; no SUM default is introduced here.
- **Saved values:** `snapshot_read` is the shared artifact-scoped AST for materialisation reuse, Decision View and edits. It keeps stable key aliases, nullable casts, coverage and Mixed flags. Read admission prevents concurrent table replacement while an admitted query is running.
- **Compilation state:** `CompilationCheckpoint` restores speculative branches in place, including pivot input caches. This keeps the compiler and its context attached to the same CTE/check containers and prevents abandoned nodes leaking into later measures. Direct transaction execution uses the same Pivot/Calendar input pipeline as preview; final mapping and filtering retain their order.
- **Capture scope:** one `PopulationCaptureSession` memoises ancestor and managed-source captures within a single metadata capture transaction. Activation starts a fresh session. The complete revision input fingerprint and population readiness checks remain deliberately intact; removing unrelated Dimensions from that fingerprint would change existing saved-build compatibility. Dirty-measure manifests and execution retain their dependency-scoped reuse.
- **Jobs:** stdlib `graphlib.TopologicalSorter` replaces custom dependency traversal, with sorted ready batches and explicit missing-parent/cycle errors. The composition root supplies the worker's store, shared handler registry, collector and workspace gate. Population-only and complete-network commands share one handler instance. `current_build_revision` shares version checking; handlers still own fencing, publication, preview and generation rules.

Library choices: retain pinned SQLGlot 27.28.1 and Lark 1.3.1, use Pydantic for contracts and stdlib graphlib for DAG ordering. SQLGlot lowers analysed operations; its general optimiser does not decide semantic policy. Hypothesis is a development-only dependency for generated dependency/order invariants. No new runtime dependency, retry framework, queue, graph database or dataframe engine is added. Retrying non-idempotent warehouse writes is outside this change.

Compatibility was checked against the preceding compiler on isolated ClickHouse 25.3: 528 combinations of aggregation method/order/NULL policy/Mixed state matched, plus quoted, generation-scoped snapshot reads. Committed operator tests cover unequal-group averages, typed Mixed/Boolean states, dependency ordering, snapshot identity and rollback. Run the full unit and isolated ClickHouse suites when modifying these boundaries; SQL-text comparison alone is insufficient.

## Persistence boundaries and component lifetimes

Services and engine coordinators do not create database clients, construct MongoDB selectors, or execute SQL/client callbacks. They orchestrate business rules and transactions, using typed metadata repositories and warehouse operations. SQL construction belongs to compilers; execution and physical object ownership checks belong to `warehouse/`. Existing engine executor/storage/retention imports are compatibility exports of those warehouse implementations.

- `repositories/metadata/` owns model, revision, object, managed-table, record, job, artifact, binding, lease and storage-resource persistence. Immutable lookup objects express domain IDs, expected versions, states and cutoffs. Only this package translates them into collection names and MongoDB selectors/operators. It rejects raw operator dictionaries. The low-level Mongo adapter owns driver calls, session propagation, indexes and schema setup.
- `warehouse/query_execution.py` owns population/value previews, Decision View reads, resolution preview/count diagnostics and profile reads. Managed view execution, planning-table execution, versioned storage and retention have dedicated warehouse adapters. Services receive rows/results and never receive a client or an executable client callback. Preview limits, ownership checks, settings and diagnostics remain unchanged.
- `MongoMetadataStore` owns the pooled MongoDB client; `ClickHouseWarehouseRepository` owns its lazy ClickHouse client and guarded execution. The application container creates services once per app/worker. No service opens another client.
- Sessionless Mongo reads reuse one document adapter and cached domain repositories for the store lifetime. Each MongoDB transaction attempt has a separate session-bound adapter; its domain repositories, record repositories and activation writer are created lazily once and reused throughout that attempt. Caches hold repository bindings, never query results. Reopening the store invalidates its read adapter. A transaction repository must never be a global singleton or be shared with another transaction.
- Warehouse query adapters, check runners, immutable check diagnostics and input verifiers are reused. Stateless filter compilation and managed-table planning use class/static operations without allocating a component per call. Planning compilation has an application-scoped facade with fresh internal compilation state. Measure/query compilation contexts, validation graphs, input snapshots and heartbeat tasks remain operation-local because they hold mutable or request-specific state.

Architecture tests reject client/driver access, raw document operations and MongoDB operator construction outside persistence infrastructure, and reject collection names/SQL generation in services. Lifecycle tests verify adapter reuse, separate transaction sessions and read-cache invalidation on close/reopen. This changes code ownership, not API payloads, metadata documents, aggregation policies, storage generations or the current-table contract.

## Contracts and compilation

Engine-owned immutable contracts include owner-qualified ColumnRef, RelationSchema (ordered IDs/types/nullability/keys/lineage), logical plans, compiled execution/check steps, captured metadata inputs, durable runs, artifacts and active bindings. Source/stage plus column ID is required; bare `col_1`, names and labels are insufficient.

Managed pivots compile explicit grouping: empty record keys group retained fields plus raw pair discriminators/values; supplied record keys merge entity attribute rows with strict cell/carried-value checks. Layout detection and data profiling are removed. Schema analysis is metadata-only; saved legacy operations remain compatible. See [managed pivot contracts](SOURCES_AND_MANAGED_TABLES.md#pivot-grouping-and-final-output-keys).

Planning compilation always applies DISTINCT to the final public output for source, Cartesian and parent-projection populations. This collapses identical intersections; NULL keys, conflicting attributes per grain and invalid dimension lookups still fail. Preview and Build compile the same output semantics.

Measure source initialisation derives SUM/equal versus repeat from each expansion axis, reversing aggregation order. Edit disaggregation is owned by MeasureEditCompiler and continues to use configured allocation. Representation boundaries round stored values to six places before downstream propagation; the policy participates in network fingerprints. See [measure execution](MEASURES.md).

Typed operators include scans/projects, Pivot, CrossJoin, DistinctProject, filters and lookup enrichment, with measure dependency DAGs/resolution operators composing further queries. Only code-owned allowlisted implementations execute; neither client payloads nor vocabulary documents register arbitrary SQL/functions.

The IR and stored semantic formula AST are independent of SQLGlot. ClickHouse adapters use pinned SQLGlot 27.28.1 for AST construction/parsing/rendering, with quoted identifiers, typed/escaped literals and validated types. No API accepts arbitrary SQL/physical execution plans. SQLGlot does not replace semantic validation or real ClickHouse tests.

Use captured input artifact names/generation tokens throughout a run, not whatever binding becomes active later. Metadata snapshots freeze definitions, not live raw rows. Materialisation captures rows read by a build without claiming a distributed snapshot across arbitrary external writers. App-imported CSV sources have no row-update API; future refresh requires explicit data-generation guarantees.

## MongoDB operational records

Keep these separate from semantic definitions:

- `engine_runs`: scoped target, expected versions, request/idempotency hash, run state, owner/lease/fence, fingerprints, candidates, timestamps and bounded errors.
- `engine_run_inputs`: one immutable captured definition/input per run/input ID, avoiding revision-sized BSON documents. Edit payloads are transient exceptions removed at completion.
- `engine_run_steps`: compile/check/create state, SQL/plan hashes, attempt/fence and timing. Recovery updates attempts; this is not a complete append-only attempt audit.
- `engine_artifacts`: owned physical kind/name, schema/lineage, plan/definition/compiler/source hashes, lifecycle, creating run and generation/storage-column maps.
- `engine_artifact_bindings`: active artifact per `(modelId,revisionId,resourceKind,resourceId)`.
- `engine_artifact_pins`: build/run input retention by `(runId,artifactId)`.
- `engine_read_leases`: renewable retention for active reads; TTL clears expired leases.
- `engine_table_resources`: stable physical table/column registry described below.

Runs dispatch managedTable, dimension, dimensionPreview and measureSet jobs; level value bindings/artifacts use measureValues. DimensionPreview jobs produce dimension artifacts without binding them. Compatible legacy managed sourceId paths remain readable. Startup backfills generic identity and replaces the source-only unique index with partial managed-source and generic target indexes. Unique managed-definition/target/idempotency/step identities and queued/lease/retirement indexes protect recovery. Deploy API/worker code together; old source-only workers cannot process the generalized queue.

## Durable execution and activation

1. Capture bounded consistent metadata/input artifacts, expected versions and idempotency hash. Pin dependencies transactionally; pin acquisition and retirement touch the same artifact record to serialize their race.
2. Queue durable work and return HTTP 202/run handle. Idempotency is model/revision scoped: same key/request replays its run; changed request conflicts.
3. A Mongo-backed worker claims a 60-second lease, increments fence and renews every 10 seconds. Expired work is recoverable by another process; no Redis/Celery or in-process-only queue is required.
4. Compile, run domain-specific checks, create/insert the candidate, inspect schema and validate full candidate. Keep diagnostics bounded without restricting checked input to preview rows.
5. In a short Mongo transaction recheck owner/fence/unexpired lease, target/revision versions, input hashes/bindings and draft rules. Revalidate downstream schema references as applicable, then activate definition/binding/run atomically. Network/edit jobs swap every affected level to one coherent generation.

Failure, cancellation, superseded input or stale versions preserve the previous definition/bindings. Current-storage builds write isolated candidates; failed work leaves live values intact. Reads remain blocked until coherent recovery succeeds. First managed enable may retain unavailable raw registration. Unrelated revision edits can conservatively supersede builds; do not automatically replan over newer intent. Cancellation fences activation but cannot promise interruption of in-flight ClickHouse calls. Shutdown/recovery leaves durable work for lease reclamation. Warehouse and MongoDB do not share a distributed transaction; correctness comes from validated writes before the fenced manifest switch.

Generic endpoints are revision-scoped `GET /engine/runs/{run}` and `POST /engine/runs/{run}/cancel`. The UI polls while open; jobs continue across reloads. No run-history UI exists yet.

## Managed view ownership

Each managed build has a unique candidate view with a reserved `__semantic_` name, hidden from catalog/raw preview. Verify ownership before recovery/collection or accepting an existing object; never replace an active view in place.

On ClickHouse 25.3, create the view then ALTER TABLE MODIFY COMMENT for its ownership marker. If interrupted between them, parse/verify the engine-owned subquery alias in `system.tables.as_select` with SQLGlot before applying the comment. Unknown ownership is retained for investigation. Pivot row expansion uses direct per-record projection; legacy/explicit merge mode retains full duplicate-cell checks. Identity/pivot semantics are in [Sources and Managed Tables](SOURCES_AND_MANAGED_TABLES.md).

## Current-table storage and safe publication

One permanent engine-owned physical table per materialised dimension holds its keys, attributes, measures and coverage/Mixed flags. Population and values remain separate **logical projections**, not duplicate physical tables. Single-source dimensions read managed views without copied populations, including during explicit dimension builds and draft previews. Derived/Cartesian dimensions have a physical population; subsequent materialisation adds measures to that same table. Raw sources retain their names and are never altered to hold semantic measures or engine columns.

Every generated physical table has a stable ordinary view. Downstream semantic reads use views; engine writes and ownership checks use physical tables. Managed source views exist with or without transformations. Identity views do not duplicate data. Input transformations remain independent per Dimension/Transaction.

`engine_table_resources` owns a canonical dimension resource shared by population/value bindings, stable physical/view names and sorting metadata. Current artifacts use `storageMode=current`. Stable physical column slots follow column IDs; a logical measure rename preserves its values and is exposed as the new name through the view. Readers resolve logical view columns explicitly; clone mutation/checkpoint code addresses physical slots. There is no `__semantic_generation` column or historical row retention. Operational run/generation IDs remain in MongoDB for coherent snapshots, stale-edit detection and audit.

**Sorting.** First population chooses `ORDER BY` from grain keys: explicitly identified time keys first; all remaining keys in ascending exact initial distinct count, ties in configured key order. Empty populations use zero counts and stable key order. Store `sortKeyIds`, `initialCardinalities` and the selection timestamp; reuse the choice for unchanged grains, even if cardinalities later change. A changed grain is a full layout rebuild. Sorting accelerates compatible leading-key filters; it does not guarantee faster arbitrary pivots or enforce uniqueness.

**Build and edits.** A compatible incremental build clones the live table with `CLONE AS`, changes only affected measure columns/dependants and removes obsolete columns from the clone. Full/population/layout builds create a replacement candidate and populate it from explicit keys/attributes, then compute measures in dependency order. Existing aggregation, NULL, six-decimal storage and AggregateFirst/CalculateFirst policies are unchanged. Failed computation leaves the live table untouched. Temporary candidates and their views are permitted only for build/preview work; after publication one permanent table remains.

**Database-side measure writes.** First/full builds insert the population and first independent measure group together with `INSERT ... SELECT`; later formula groups read completed candidate checkpoints. Compatible incremental builds clone the current table and change only invalidated measures/coverage flags, preserving untouched values and edits. A new Transaction does not refresh other Transactions' measures. Dirty formula dependencies are written before consumers; unchanged inputs read saved values, including edits. Measures sharing a compatible aggregation can reuse the compiler's shared native read. Aggregation, disaggregation and rounding stay in the existing semantic operators; the writer chooses no aggregation defaults.

For each subsequent changed group, capture only keys and changed columns once in an owned temporary MergeTree stage. Validate uniqueness, non-NULL keys/results and row count there; populate a temporary Join-engine lookup, prove complete target-key coverage, then run one synchronous `ALTER ... UPDATE` for that group. Verify stored values with a server-side mismatch count. Scratch fields use ordinal aliases so user column names cannot collide with internal names. Python receives schema, scalar summaries and job status, never materialised measure rows or full read-back dictionaries. This replaces the 1,000-cell parameter-array writer.

Interactive edits additionally track changed-cell key sets. A fenced temporary ClickHouse patch freezes the rounded changes/weights once; only dependent formula cells and complete affected aggregation groups are recomputed. The clone retains untouched content. Each affected measure uses a typed-key `IN` predicate and a subset-coverage check, with `updatedRows` reported per group; identical stored-value edits issue no row mutations. Completed private grains checkpoint later calculations. Temporary patch ownership is recorded before creation, removed on success/failure, and recovered immediately after interrupted terminal attempts. This is operational staging, not an edit journal. See [cell-scoped refresh](DECISION_VIEW.md#cell-scoped-dependency-refresh).

The lookup has an explicit byte ceiling equal to the captured query-memory budget and fails rather than silently truncating. It resides in ClickHouse memory and does not spill; narrow stages/candidates also need temporary disk space. Keep concurrent builds bounded. Cancellation fences groups and publication; an in-flight SQL call may finish on the isolated candidate. Cleanup cancels unfinished candidate mutations before releasing their lookup. Owned stage/lookup names derive from the candidate and are removed on success/failure; durable candidate recovery removes leftovers after a crash. One permanent table remains after publication. Adding a measure preserves other measures' edits; changing that measure's source/policy/population or Full Refresh may replace its edits, because there is no durable override journal.

Publication requires an Atomic ClickHouse database. Validate first, journal candidate/original table UUIDs in MongoDB, then `EXCHANGE TABLES`; first publication renames the engine candidate to its stable name. Source names are unaffected. Refresh the stable view, commit bindings and delete the replaced copy. Exchange is metadata work independent of row count; cloning depends on part count and rebuild/cleanup still cost resources. Multiple exchanges are not a network-wide transaction: retain the read/edit barrier until the network finishes. Failures before metadata activation reverse exchanges; interrupted attempts recover by recorded UUIDs, not names alone. Cleanup is idempotent and uses an indexed pending queue, checked on worker startup and by the collector. Reversible recovery has an artifact-level renewable lease so multiple workers cannot undo the same exchange twice. Completed artifacts are not repeatedly rescanned for warehouse cleanup. Draft previews remain isolated until Save and expire through retention if abandoned.

Older row-generation formats remain readable only for explicit migration. Run the one-time consolidation script described in [Operations](OPERATIONS.md#one-time-current-storage-consolidation); it preserves active edited values, checks row counts/content hashes, updates active bindings and drops only obsolete owned engine tables. It never rewrites raw sources. No source/table-name migration runs at application startup.

Object-owned input pivots reuse ManagedTablePlanner/ClickHouseCompiler through `engine/transformations/inputs.py`. Planning RelationScan may carry an optional logical transform for dimension lookups. Measure compilation caches each owner/artifact/pivot input as a CTE and carries its full-input assertions into the execution plan. This supports independent Dimension/Transaction transforms without shared-source mutation or extra physical tables; calendar and multi-grain stages consume the resulting schema.

Final-output filters use the shared typed engine module and nested AND/OR editor. See [Filters](FILTERS.md) for stage placement, scalar operators, NULL semantics, schema APIs and compatibility.

### Schema reuse and incremental materialisation direction

Versioned table builds reuse the authoritative schema returned by `TableStorage.prepare` for column slots, insertion metadata and artifact output. They do not rerun the full compiled SELECT with LIMIT 0 in the executor. Legacy builds retain their header-discovery path. This is a performance-only change; both pre/post input checks and candidate table validation remain intact.

Incremental materialisation is implemented by `engine/execution/builds/incremental.py` and `services/incremental_builds.py`. `materialisationManifest` on each values artifact stores a policy version, per-measure/per-target evaluation fingerprints and an output-layout hash. Fingerprints include the recursive formula dependency closure, native/Base/target population artifacts and projection ancestry, relevant Dimension definitions, Transaction transformations/mapping, managed input artifacts and numeric/materialisation/compiler policies. Unrelated new measures/levels do not invalidate existing representations. Edit allocation/permission and output labels are separated from evaluation; changed labels/layout are copied into a new schema without reloading unchanged values.

Job manifests are stored per level in `engine_run_inputs` (rather than one unbounded measure × level map on the run document), keeping individual MongoDB documents bounded. Incremental Build captures and pins a coherent set of active values alongside its ordinary inputs. Matching representations read explicit columns through the captured current view; changed/new representations use the existing compiler and can read valid upstream/native representations. AggregateFirst still recalculates from dependencies at the requested grain; CalculateFirst still rolls up its native results. New referenced measures load their own source, even if another edited measure references the same source column. The engine never substitutes that other measure's edits implicitly.

A no-change job validates and reuses current bindings without data writes. Incremental builds evaluate only invalidated measures/dependants in a clone, preserving unchanged values and edits. Full Refresh rebuilds from sources and replaces separately materialised edits. Source-backed edits already live in the source and survive refresh. Shared native aggregations, dependency pruning and per-measure stored checkpoints bound SQL expansion. Schema removal physically drops columns in the candidate before exchange.

**Read barrier and budgets.** Queueing a network build or another live-table writer rejects new Decision View queries/edits and values previews with 503; existing read leases drain before publication. Metadata/status remain available. Mutations are synchronous and fenced between dependency groups, with server-side persisted-value verification. Failed network publication keeps reads blocked until recovery succeeds. Per-job memory limits flow to children without changing semantic evaluation fingerprints. Actual execution SQL is captured separately from compiler plans.

Compatible pre-upgrade artifacts establish their baseline from immutable `engine_run_inputs`, including artifacts from edit jobs. Current metadata must never be guessed to be the old baseline. Missing captures or incompatible numeric/compiler policies require explicit Full Refresh and leave existing values intact. Each full build and edit writes a current manifest for subsequent incremental reuse.

Freshness uses supported managed-artifact/definition versions and population artifacts. Rebuilding a managed source signals new input data and invalidates its dependent measures/formulas. Arbitrary direct ClickHouse row mutations do not advance those tokens: use explicit **Full Refresh** for them. Full Refresh reloads all sources and replaces separately materialised manual edits; incremental builds preserve unchanged values/edits and recompute only invalidated representations. Changing a measure's source/semantic policy or its required populations can therefore replace that affected measure's edits; this is not a durable edit-replay journal.

## Formula compilation boundary

The `formula_language` package separates Lark syntax, versioned semantic AST/resolution, type/function contracts and SQLGlot scalar lowering. `engine/measures/counting.py` plans aggregate arguments at the measure’s Output Dimension before projecting to output grain. Relational planners consume these expressions; repositories alone execute warehouse I/O. Grammar/parser instances are cached; request resolvers and build compilers hold only operation-local state. Legacy saved ASTs are accepted; versioned authoring source is reparsed on validation/save. Window/recurrence semantics remain future extensions described in [Measures](MEASURES.md#formula-language-architecture).


## Imports and dependency direction

Runtime imports belong at module scope, grouped as standard library, third-party and local imports. `TYPE_CHECKING` imports remain guarded for annotations. Do not hide a runtime dependency cycle inside a function. Architecture tests reject nested runtime imports and circular module dependencies.

ClickHouse quoting lives in `warehouse/sql.py`, independent of repository/client creation. Shared measure value-column names live in `engine/measures/contracts.py`, independent of the measure compiler. `CompilationContext` uses the base ClickHouse compiler for Pivot/Calendar inputs, without depending on the Dimension renderer or MeasureCompiler. This keeps input compilation usable by both compilers without a cycle. Activation persistence receives the transaction's existing repository bundle rather than importing its factory back through the package.

## Exposing final SQL

**View SQL** sits next to Preview in Dimension and Transaction editors and managed-table configuration. It opens the current compiler output in a read-only dialog with **Copy SQL**. SQL is formatted from the same SQLGlot AST as execution; identifiers, transformation stages, filters and NULL handling remain unchanged. The exposed query is complete, before the 50-row preview limit. Source data previews also show their full source SELECT.

The existing preview APIs accept `?sql_only=true`; they validate and compile the current request but skip final output execution, output validation queries and row-count estimates. Input metadata verification and multi-grain profile discovery can still read the source. SQL viewing does not save definitions, create population/value tables or materialise values. All generated literals remain safely quoted. This is an inspection capability, not an endpoint for submitting arbitrary SQL.

Build Semantic captures the final values SELECT in its successful per-Dimension execution step. `GET /measures/execution/levels/{dimensionId}/sql` follows the active values binding to that artifact's run and returns its captured query, including incremental reuse and policy-driven joins. It does not regenerate SQL from definitions that may have changed since the build. SQL from older builds may be absent; a full refresh captures it. Generation references describe the execution at that time and can later be retired. No generated SQL is stored in browser preferences or added to the semantic definition.

## Transaction-driven representation placement

`engine/graph/representations.py` is the shared placement policy for compilation, incremental manifests and build explanations. It discovers Transaction-native grains plus Base as shared targets, and each calculated measure's own output as a required target. Only proven rollups populate other Transaction-native targets; distribution is restricted to the established Base contract. Captured population inputs still include supporting Dimensions, but the measure build iterates only placement manifests and atomically removes obsolete values bindings. No extra MongoDB property or migration of authored objects is required.

`engine/decision/attributes.py` builds the native/Base attribute catalog from declared output schemas and semantic coordinates. Equivalent references are returned as aliases for browser-preference restoration; names never prove identity. Decision queries can aggregate independently stored inputs before joining at the requested grain. Source schemas and lease/generation fencing remain unchanged.

## Derived Dimension Save coordination

`services/dimension_commands.py` owns the Save-and-build command; the UI sends one command and polls its run. `SemanticNetworkService` and its worker handler support a `dimensionSet` population-only scope containing the requested derived Dimension and its projection ancestors. They reuse existing population jobs, fences, input fingerprints, cancellation and table storage, then stop before submitting measures. Shared app-scoped services are injected through the container; no service creates database clients or executes SQL. Source-backed metadata CRUD stays metadata-only.

## Executed SQL inspection

Materialised tables expose **View Output SQL** (`GET /measures/execution/levels/{id}/output-sql`) for the exact saved-table preview SELECT, including its 50-row limit, and **View Build SQL** (`.../build-sql`) for actual recorded statements, parameters and execution settings from the owning build run. A multi-target build trace includes its other target stages. Historical builds without execution captures return an explicit unavailable message; logical compiler plans are never labelled executed Build SQL. Captures are bounded (4 MiB / 512 statements per attempt); omitted statements are reported. Viewing/copying never executes SQL.

Decision View query responses include the actual grouped read SQL (including group-limit enforcement). Its **View Output SQL** button uses the last displayed result, avoiding recompilation against changed selections. Output formatting remains two decimals in the pivot; SQL/data retain their configured precision.

## Readable managed-source view names

New managed-source views use `dim_{actual_source_table_name}_{artifact_id}` or `trans_{actual_source_table_name}_{artifact_id}`. Names retain ASCII case, replace punctuation with underscores and bound the readable part to 80 characters. Source table names/semantic IDs are unchanged. Explicit Transaction use selects `trans`; Dimension use selects `dim`; a shared source with both uses one canonical `trans` view. Before semantic objects exist, the existing numeric/non-numeric upload classification supplies the fallback.

Full Semantic Refresh prepares any legacy/misclassified source views through normal durable managed-view repair builds before population/value work. It preserves saved transformation definitions and column IDs, then rebuilds dependent populations/values as part of that explicit Full Refresh. Already-readable views are reused. Incremental builds retain existing source artifacts and edits. No rename/migration is executed on deployment; old views retire through the existing retention/pin/lease-aware collector.


## Temporal calculations and conversion ownership

`formula_language/catalog.py` owns function signatures and display groups; `formula_language/temporal.py` owns reducer/offset validation. `engine/measures/temporal.py` lowers fixed-grain windows into ClickHouse calendar RANGE frames and separate stages for nesting. `engine/decision/temporal_impact.py` expands edit key sets, joins by affected series/reset keys and preserves complete history before restricting changed output cells. No Python row buffering is introduced.

`engine/measures/conversion.py` LEFT JOINs a stored factor to native values and validates usable factors. Factors use ordinary Transaction/reference-measure metadata, storage, dependency ordering and incremental source fingerprints. `validation/temporal.py` and `validation/conversions.py` enforce fixed calculation grain and factor determinacy before execution. Services/repositories/warehouse adapters retain their existing responsibilities and client lifetimes. See [measure semantics](MEASURES.md#stored-conversion-factors-and-converted-references) for conversion grain and edit boundaries.

## Independent Transactions: source-backed storage

An unbound Transaction with an identity managed input and no active Pivot, Date Resolution or Filters uses its existing physical source as the source of truth. Its logical grain remains a DISTINCT query; it does not allocate an engine table-resource entry or a permanent `grain_` copy. The source must not also populate another Transaction/Dimension: shared-source or transformed modelling retains the existing materialised path because write-through needs coordinated/invertible mappings.

`engine/graph/source_storage.py` selects this strategy from captured metadata. The value artifact has `storageMode=source`, `kind=view`, `sourceId`, `sourceTableName` and the usual key/measure column maps. One owned `trans_{source}_values_{id}` view exposes policy-aggregated values. After successful network publication the identity input is a metadata reference (`kind=source`, `storageMode=source_input`) to the imported physical table, and its redundant owned view is removed. Raw previews, discovery and compilation read that table directly; schema checks and managed definitions remain intact. The collector never drops a `source_input` physical table. Shared/transformed workflows retain their distinct input/output contracts. CalculateFirst/AggregateFirst retain their ordering semantics, but source-backed calculated outputs are view-evaluated, not separately persisted numeric columns. View definitions are rebuilt from source inputs, never chained through a prior output view. References sharing the same source column intentionally observe each other's edits. External source changes are visible through the view; preview totals are counted live.

Source-backed edits freeze their native patch with the existing bounded edit-cell stage, clone the source into an owned temporary MergeTree, and allocate edited native values into its underlying records in ClickHouse. Only the edited value column changes. None repeats; Equal splits SUM totals and repeats other reducers; Weighted by self uses the configured native reducer to normalise existing physical values, preserving NULL records. Explicit weighted allocation needs a basis column from the same Transaction and normalises it with the configured reducer. Weighted writeback verifies the resulting native value; an unrepresentable weight/aggregation combination fails before publication. COUNT/COUNT_DISTINCT references are read-only because changing record counts cannot be implemented by updating values. Grain-key columns cannot be edited as measures. Conversion edits inverse-convert to source units before allocation.

Edited numeric columns widen to Nullable(Float64) on the private clone so fractional and NULL values are representable. A fenced publication exchanges the clone with the original source name and commits source/managed schema metadata and output fingerprints together. Legacy identity views are refreshed only while transitioning to a direct input reference. Existing connections/column IDs remain stable. Source UUID/schema/part-version checks reject intervening external writes instead of silently overwriting them. Application read admission is blocked and prior leases drain before publication. Direct external writers must still coordinate with application builds; ClickHouse and MongoDB do not provide a distributed transaction.

`warehouse/source_values.py` journals UUIDs before exchange, owns only its output view/temporary clone/lookup, and restores the source and any legacy managed-view schema when metadata publication fails. `warehouse/source_output_views.py` exchanges the checked candidate view into the existing output name, preserving that name for edits, incremental builds and Full Refresh. It restores the old view on failed metadata publication and removes replaced candidate views after success. Candidate views are temporary, not retained generations. Superseded engine-owned source views from earlier builds are also retired after checking bindings, terminal runs, read leases and active pins; imported tables and unrelated views are excluded. Input-reference consolidation commits in the same metadata transaction; owned input views are retired only after that commit. Successful cleanup drops the old source copy; interrupted cleanup resumes through existing recovery leases. No original-value snapshot/edit journal is retained. Immutable run inputs preserve metadata/SQL history, not historical source data. Read-only and no-op builds create no physical data copy; source edits use temporary physical stages only.

Existing independent engine-owned table outputs require **Full Semantic Refresh once** to adopt source-backed storage. Existing source-backed two-view outputs consolidate automatically on the next build, including an incremental build; their source values/edits remain unchanged. A source-only layout fingerprint invalidates the old two-view layout without invalidating bound outputs.

Incremental builds refuse a silent table-to-source switch that could discard old materialised edits. After successful adoption, obsolete engine-owned table/view resources retire after reader drainage; imported source tables are never retirement candidates. Subsequent Full Refresh uses the already-edited source, so source-backed edits survive. Dimension-bound output edits continue using the existing separate current-table storage.
